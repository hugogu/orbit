# Localization

ORBIT supports Simplified Chinese, English, and Japanese. The language control is in the header on desktop and mobile. A language change updates interface text, accessibility labels, scene labels, body profiles, sourced fact cards, settings, and astronomy results without restarting the simulation or resetting the camera.

## Language selection

The application resolves a supported language in this order:

1. The `lang` URL parameter on the explorer, for example `/?lang=ja#moon-titan`.
   Localized body profiles use regional path segments such as `/zh-CN/bodies/sun`, `/en-US/bodies/sun`, and `/ja-JP/bodies/sun`.
2. The last explicit selection, saved as `orbit-language` in local storage.
3. The first supported language in the browser's preferred languages.
4. Simplified Chinese as the fallback.

Regional variants such as `en-GB` and `ja-JP` resolve to the corresponding supported language. Profile language switches replace the regional path segment while preserving the body ID and other URL state; explorer switches keep using the `lang` query parameter. Legacy `/en/...` and `/ja/...` profile links permanently redirect to their regional paths. Storage is optional, so switching still works when browser privacy settings block storage. Static HTML starts in the fallback language; browser preferences are applied after hydration. The document language, title, and description then follow the selection.

The build-generated sitemap lists every localized profile URL. Each profile entry repeats the complete `xhtml:link rel="alternate"` set for `zh-CN`, `en-US`, `ja-JP`, and `x-default`, so the language and region variants remain reciprocal.

## Add a language

1. Copy [`lib/i18n/messages/zh-CN.json`](../lib/i18n/messages/zh-CN.json) to a catalog named for the new language, such as `fr.json`.
2. Keep the source keys and translate their values. Include body descriptions, fact cards, units, notices, and accessibility text as well as buttons. Preserve every `{{placeholder}}` exactly.
3. Import the catalog in [`lib/i18n/index.ts`](../lib/i18n/index.ts) and add one entry to `languages`, including its native `name`, compact `short` label, `intl` locale, and `messages`.
4. Run `npm test`, `npm run lint`, `npx tsc --noEmit`, and `npm run build:vercel`. Check desktop, phone portrait, and phone landscape layouts in the exported site, including a moon profile and a completed astronomy calculation.

The registry defines the TypeScript `Locale` union, language picker options, resource registration, and preference detection. No changes to the renderer or astronomy engine are needed. English and Japanese currently demonstrate left-to-right localization; adding a right-to-left language also requires document direction and layout testing.

## Translate application text

React components use `useI18n()` from `lib/i18n/provider.tsx`:

```tsx
const { t, locale } = useI18n();
return <button>{t('返回{{name}}', { name: t(body.name) })}</button>;
```

Catalogs use complete Chinese source strings as keys. Translate whole sentences rather than concatenating fragments so each language can reorder placeholders. Add new keys to all three catalogs. Changing a source key requires updating its translations too.

[i18next](https://www.i18next.com/) handles lookup, fallback, interpolation, and plurals. A missing translation falls back to Chinese, then to the source string. Each language has a separate cached translator; switching one browser view never mutates a global language instance. React and DOM `textContent` escape the rendered strings; do not render translation values through `innerHTML` or `dangerouslySetInnerHTML`.

Pass `count` for pluralized messages. For example, English defines `{{count}} 天 / 秒_one` and `{{count}} 天 / 秒_other`; other languages may add the plural suffixes required by [i18next's plural rules](https://www.i18next.com/translation-function/plurals). Tests allow these language-specific variants and verify their placeholders against the source key.

Use the selected locale for human-readable number and event-date formatting. The shared simulation timestamp remains explicitly UTC. Body IDs, URL hashes, texture names, orbital data, physical values, source links, and astronomy query inputs are language-independent. Astronomy errors and results remain in their original data form until presentation, so existing results can be translated without recalculation.

## Knowledge and scene labels

Educational datasets retain their source text and references. `CuriosityCard` translates each fact and interpolates its named values at display time, preserving the chosen fact when languages change. New educational content must have entries in every catalog; the tests render every fact in every registered language. Planets, moons and comets have 30 entries each; named asteroids have six sourced orbital and scale notes.

Three.js uses `translator(locale)` for labels. The animation loop refreshes planet and moon labels only when the locale changes. It does not recreate the scene, reload textures, or reset simulation time. Comet labels also receive the current translator. Keep this behavior when adding new scene objects.
